# ISS-0002 — Move blocking filesystem and ffmpeg work off Tauri's main thread

GitHub: [#2 — Move blocking filesystem and ffmpeg work off Tauri's main thread](https://github.com/digimata/terrazzo/issues/2)

## Summary

All current Tauri commands are synchronous, so recursive scans, large file copies, and ffmpeg execution run on Tauri's main thread and can freeze the window.

## Evidence

- `set_workspace` performs a recursive scan synchronously.
- `rescan` performs a recursive scan synchronously.
- `import_files` copies every selected file synchronously.
- `generate_poster` waits for ffmpeg synchronously.
- All four functions in `src-tauri/src/commands.rs` use synchronous `#[tauri::command]`.

## Proposed change

1. Make the command boundary asynchronous.
2. Run blocking filesystem and process operations through `tauri::async_runtime::spawn_blocking` or a dedicated workspace worker.
3. Model poster generation as a cancellable background job.
4. Keep watcher reconciliation ordered and coalesce redundant scans.

## Acceptance criteria

- A recursive scan does not block window interaction.
- Importing a large video does not block window interaction.
- Poster generation can report progress or pending state and can be cancelled.
- Command errors retain the existing structured `{ code, message }` shape.
- An automated test covers command completion and error propagation.
