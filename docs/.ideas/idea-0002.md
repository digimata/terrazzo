# IDEA-0002 — Theme system and visual personalization

> Terrazzo should have a coherent theme system that can change the appearance of the application, canvas, cards, editor, and media views without coupling product behavior to one visual treatment. This is a provisional direction, not a PRD requirement.

## 1. Judgment

A theme system would suit Terrazzo particularly well because the canvas is both a working environment and a visual space. People should be able to make it feel like their own without compromising legibility, interaction states, or media presentation.

The application should first establish a small semantic token system rather than exposing arbitrary CSS. Built-in themes can validate that the architecture works. User-authored themes can follow once the token contract is stable.

## 2. Proposed experience

### 2.1 — Built-in themes

- Terrazzo ships with a small set of polished themes, including dark and light treatments.
- A theme changes the full application coherently: canvas background, grid, cards, typography, controls, selection states, editor, and media-detail views.
- The active theme can follow the operating system or be selected explicitly.
- Switching themes updates the interface immediately and persists across launches.

The themes should feel intentionally designed rather than like mechanical color inversions. A theme may vary color, contrast, surface treatment, type choices, grid visibility, and restrained decorative details while preserving layout and behavior.

### 2.2 — Custom themes

A future custom theme format may allow a user to define semantic values such as:

- canvas and elevated surface colors;
- primary, secondary, and muted text;
- borders, shadows, and grid treatment;
- selection, focus, warning, and error states;
- folder, document, image, and video accents;
- editor syntax colors;
- typeface preferences and limited shape characteristics.

Custom themes should be portable local files with a versioned schema. Terrazzo should validate them, reject unsupported values safely, and fall back to a built-in theme when a file is missing or invalid.

Direct arbitrary CSS injection is not part of this idea. A constrained schema is more durable, safer, and easier to evolve.

### 2.3 — Theme scope

The initial preference should be application-wide. A later version may allow a workspace to request or remember a theme, but opening a workspace should never make the interface unreadable or unexpectedly override accessibility preferences.

If workspace-specific themes are introduced, the application should distinguish between:

1. the user's global interface preference;
2. an optional workspace visual identity; and
3. non-overridable accessibility constraints.

## 3. Design and architecture implications

- Components should consume semantic tokens rather than hard-coded colors or theme-specific class names.
- The token layer should cover both the React interface and tldraw-backed canvas elements.
- CodeMirror syntax highlighting should derive from the same theme definition while retaining editor-specific token roles.
- Native Tauri window treatment should be synchronized where the platform APIs permit it.
- Theme preferences belong in application settings. Portable custom-theme files may live in an application-level themes directory rather than inside a workspace.
- The schema needs a version so themes can be migrated as semantic roles evolve.
- Theme changes should not rebuild the canvas store, disturb selection, reset the camera, or remount active editors.

## 4. Constraints

1. Every bundled theme must meet defined contrast requirements for text and interactive states.
2. Selection, keyboard focus, errors, missing files, and disabled controls must remain distinguishable without relying on hue alone.
3. Media should remain visually faithful; themes may change its framing but not apply effects to the underlying asset.
4. Theme loading must be local and deterministic. A theme must not fetch remote fonts, scripts, styles, or images at runtime.
5. A malformed custom theme must not prevent Terrazzo from opening.
6. Theme support should not become a prerequisite for the v0 canvas unless it is explicitly promoted into scope.

## 5. Open questions

1. Should workspace-specific themes exist, or should themes remain exclusively personal application preferences?
2. Which properties belong in the stable theme schema, and which should remain controlled by Terrazzo?
3. Should custom themes permit bundled local fonts, or only reference fonts already installed on the system?
4. Is a JSON or TOML theme file sufficient, or would an in-application theme editor eventually be valuable?
5. Should canvas grid visibility and density be theme properties or independent workspace/view preferences?
6. How should a workspace suggest a visual identity without overriding the user's accessibility settings?

## 6. Promotion criteria

Promote this idea when visual customization becomes an implementation priority. Promotion requires:

1. A defined semantic token inventory covering the application, canvas, editor, and media views.
2. A decision on application-wide versus workspace-specific scope.
3. Accessibility acceptance criteria for every bundled theme.
4. A versioned custom-theme schema if user-authored themes are included.
5. PRD requirements and GitHub issues for the accepted implementation slices.
