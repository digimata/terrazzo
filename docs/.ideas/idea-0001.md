# IDEA-0001 — Default workspace, workspace switcher, and CLI

> Terrazzo should normally open directly into a saved default workspace. A workspace manager should be available inside the application, and a CLI should open or initialize workspace roots. This is a provisional direction, not a PRD requirement.

## 1. Judgment

The current start screen should not become Terrazzo's normal launch experience. It is acceptable as temporary first-run scaffolding.

Once a default workspace exists, launching Terrazzo from a macOS app launcher should open that workspace immediately. Workspace selection should remain available through a compact in-application switcher modeled on Spatial's workspace menu.

## 2. Proposed experience

### 2.1 — Application launch

- Terrazzo stores one default workspace in application-level settings.
- A normal application launch opens the default workspace directly.
- The application does not show an intermediate start screen when the default is available.
- If no default exists, or its directory is missing or inaccessible, Terrazzo opens the workspace manager.
- Opening a workspace makes it eligible to become the default. The exact default-selection interaction remains undecided.

### 2.2 — Workspace switcher

- A compact switcher is accessible from the main canvas.
- It lists registered workspaces and identifies the active workspace.
- Selecting a workspace switches the single active window to it.
- A plus action registers or initializes another workspace.
- Keyboard shortcuts may select frequently used workspaces.
- v0 still has one active workspace at a time. This idea does not require simultaneous multi-workspace windows.

![Spatial workspace switcher reference](assets/idea-0001-workspace-switcher-reference.png)

The reference establishes the interaction pattern: a small list of named workspaces, a clear active state, shortcuts, and a nearby add action. It does not prescribe Terrazzo's final visual styling.

### 2.3 — Command-line interface

```text
terrazzo
terrazzo .
terrazzo <path>
terrazzo init
terrazzo init <path>
```

Provisional behavior:

| Command | Behavior |
| --- | --- |
| `terrazzo` | Open the saved default workspace. Open the workspace manager if no usable default exists. |
| `terrazzo .` | Open the current directory only if it is a workspace root. |
| `terrazzo <path>` | Open the given directory only if it is a workspace root. |
| `terrazzo init` | Initialize the current directory as a workspace, then open it. |
| `terrazzo init <path>` | Initialize the given directory as a workspace, then open it. |

An existing workspace root is identified by its root-only `.canvas/workspace.json`. Passing a descendant directory or an uninitialized directory to `terrazzo .` or `terrazzo <path>` returns a non-zero error and suggests `terrazzo init`. It does not silently search upward or initialize the directory.

If the desktop application is already running, the CLI should route the requested workspace to that instance rather than opening an independent state owner.

## 3. Product and architecture implications

- The registered-workspace list and default selection belong in application settings outside every workspace.
- `.canvas/workspace.json` remains the durable identity and root marker for each workspace.
- Startup becomes a resolver: explicit CLI path, then saved default, then workspace manager.
- The packaged application needs a companion `terrazzo` executable that can activate or communicate with the GUI process.
- Workspace switching must revoke the old root's watcher and asset authority before enabling the new root.
- Missing defaults remain registered but show a clear unavailable state until relocated or removed.

## 4. Open questions

1. Does opening a workspace automatically make it the default, or is default selection explicit?
2. Should `terrazzo init` require confirmation before creating `.canvas/workspace.json`?
3. Should the workspace manager include recent unregistered folders as well as registered workspaces?
4. Should CLI activation reuse the current window or permit an explicit new-window option later?
5. How should a moved workspace be reconciled with its durable `workspaceId`?

## 5. Promotion criteria

Promote this idea when the launch and workspace-management model is ready to replace the temporary start screen. Promotion requires:

1. PRD requirements for default launch, workspace registration, switching, and CLI behavior.
2. A v0 scope decision on which parts ship initially.
3. An ADR if CLI-to-GUI activation or single-instance ownership changes the runtime architecture.
4. GitHub issues for the accepted implementation slices.
